1. Why LLM apps fail differently1. ليه تطبيقات الـ LLM بتفشل بشكل مختلف

"Software fails loudly. Models fail quietly." A crash gives a 500; a bad answer comes back 200 OK and reads beautifully. For LLM apps add:

  • No ground truth at request time: nobody tells us if an answer was right.
  • Non-determinism: the same input can pass twice and fail once.
  • The prompt is production config and can change without a deploy.
  • Cost is per token: a bug shows up on the invoice.
  • Failures look fluent: confident text, not a stack trace.

The NYC "MyCity" RAG bot gave illegal advice for five months; it had no golden evaluation set. "A disclaimer is not a control, and a feedback form is not a metric."

"السوفتوير بيفشل بصوت عالي. الموديلات بتفشل في صمت." الـ crash بيدي 500؛ لكن الإجابة الغلط بترجع 200 OK وشكلها حلو. وفي تطبيقات الـ LLM كمان:

  • مفيش إجابة صح وقت الطلب: محدش بيقولنا الإجابة كانت صح ولا لأ.
  • مش ثابت: نفس المدخل ممكن ينجح مرتين ويفشل مرة.
  • الـ prompt إعداد production وممكن يتغير من غير deploy.
  • التكلفة بالـ token: الـ bug بيبان في الفاتورة.
  • الفشل شكله سليم: كلام واثق، مش stack trace.

بوت "MyCity" بتاع نيويورك (RAG) فضل يدي نصايح مخالفة للقانون خمس شهور؛ ومكانش عنده أسئلة ذهبية للتقييم. "الـ disclaimer مش حماية، وفورم الـ feedback مش metric."

2. The golden set2. الأسئلة الذهبية

A golden set is a fixed, versioned list of test questions with the articles that should be retrieved and a reference answer. Ours has at least 50 questions:

  • 25 in Arabic and the same 25 in English (mirrored), so we can compare languages fairly;
  • categories: normal in-scope questions, questions about repealed articles, off-topic questions that must be refused, multi-article questions, and prompt-injection attempts;
  • stored in data/golden/golden_set.jsonl, tracked by DVC, never edited silently. A moving test set makes every comparison meaningless.

"50 well-chosen items beat 5,000 scraped ones." Every bad answer found later in production becomes a new golden item.

الـ golden set ليستة أسئلة اختبار ثابتة وليها version، ومع كل سؤال المواد اللي المفروض ترجع وإجابة مرجعية. عندنا على الأقل 50 سؤال:

  • 25 بالعربي ونفس الـ 25 بالإنجليزي، عشان نقارن اللغتين بعدل؛
  • أنواع: أسئلة عادية في نطاقنا، أسئلة عن مواد ملغية، أسئلة بره الموضوع لازم نرفضها، أسئلة محتاجة أكتر من مادة، ومحاولات prompt injection؛
  • متخزنة في data/golden/golden_set.jsonl ومتتبعة بـ DVC، ومحدش يعدّل فيها من تحت لتحت. لو مجموعة الاختبار بتتحرك، كل مقارنة ملهاش معنى.

"50 سؤال متختارين صح أحسن من 5,000 متجمعين عشوائي." وأي إجابة وحشة نلاقيها بعدين في الـ production بتتحول لسؤال ذهبي جديد.

3. RAGAS metrics, and what each one blames3. مقاييس RAGAS، وكل واحد بيلوم مين

RAGAS uses a judge LLM to answer small yes/no questions and turns them into 0–1 scores. Each metric points at a different part of the pipeline:

RAGAS بيستخدم LLM كحَكَم يجاوب أسئلة صغيرة آه/لأ ويحولها لدرجات من 0 لـ 1. وكل مقياس بيشاور على جزء مختلف في الـ pipeline:

MetricQuestion it answersبيجاوب على إيهBlames
FaithfulnessSplit the answer into claims; what share is supported by the retrieved articles?بنقسّم الإجابة لجمل؛ كام نسبة منها ليها دليل في المواد اللي رجعت؟generator
Answer relevancyDoes the answer address the question? (questions regenerated from the answer are compared with the real one)الإجابة بترد على السؤال؟ (بيطلع أسئلة من الإجابة ويقارنها بالسؤال الحقيقي)generator
Context precisionAre the retrieved articles mostly useful, and are the useful ones ranked first?المواد اللي رجعت أغلبها مفيد؟ والمفيد في الأول؟retriever / reranker
Context recallDid retrieval find everything the reference answer needs? (needs a reference)الـ retrieval جاب كل اللي الإجابة المرجعية محتاجاه؟ (محتاج إجابة مرجعية)retriever

Reading them together tells you what to fix:

  • low recall, high precision → raise top-k, split long articles, or try another embedding model;
  • high recall, low precision → the reranker or a lower top-k;
  • both high but low faithfulness → the prompt or the generator model.

Note: "a confidently wrong document produces a perfectly faithful wrong answer". Faithfulness checks support, not truth, which is why retrieval quality is measured separately. And "absolute numbers lie, deltas do not": compare runs on the same frozen set and the same judge.

لما تقراهم مع بعض بتعرف تصلّح إيه:

  • recall قليل وprecision عالي ← زوّد الـ top-k، أو قسّم المواد الطويلة، أو جرّب موديل embedding تاني؛
  • recall عالي وprecision قليل ← الـ reranker أو top-k أقل؛
  • الاتنين عاليين بس faithfulness قليل ← المشكلة في الـ prompt أو موديل الكتابة.

خد بالك: "مستند غلط وواثق بيطلع إجابة غلط بس أمينة جدًا للمصدر". الـ faithfulness بيشيك إن فيه دليل مش إن الكلام صح، وعشان كده جودة الـ retrieval بتتقاس لوحدها. و"الأرقام المطلقة بتكدب، الفروق لأ": قارن الـ runs على نفس الأسئلة الثابتة وبنفس الحَكَم.

4. LLM-as-a-judge, calibrated4. الـ LLM كحَكَم، بعد المعايرة

RAGAS is itself a judge, "not a measurement". We also write our own judge: an explicit rubric (criteria, a 1–5 scale, an example for each score) for legal answers: correct article, correct rule, no invented conditions, correct refusal.

Calibrate before trusting it. You hand-label 20 answers; the judge labels the same 20; we report the agreement rate. Below roughly 80% the judge is "a random number generator with good grammar". We also test three known biases:

  • position bias: swap two answers; does the verdict flip?
  • verbosity bias: does the longer answer win regardless of quality?
  • self-preference: does the judge prefer answers from its own model family?

The judge is pinned to one model version at temperature 0. Judges are weaker at splitting Arabic text into claims, so scores are reported per language and never pooled.

RAGAS نفسه حَكَم، "مش جهاز قياس". وبنكتب كمان حَكَم بتاعنا: معايير واضحة (البنود، ومقياس من 1 لـ 5، ومثال لكل درجة) للإجابات القانونية: المادة صح، القاعدة صح، مفيش شروط متألفة، والرفض في مكانه.

عايره قبل ما تثق فيه. إنت هتقيّم 20 إجابة بإيدك؛ والحَكَم يقيّم نفس الـ 20؛ ونكتب نسبة الاتفاق. لو أقل من 80% تقريبًا يبقى الحَكَم "مولّد أرقام عشوائي بقواعد لغة سليمة". وبنختبر تلات انحيازات معروفة:

  • انحياز المكان: نبدّل مكان إجابتين؛ الحكم بيتقلب؟
  • انحياز الطول: الإجابة الأطول بتكسب مهما كانت جودتها؟
  • انحياز للنفس: الحَكَم بيفضّل إجابات من نفس عيلة الموديل بتاعه؟

الحَكَم متثبت على نسخة موديل واحدة وtemperature 0. والحكام أضعف في تقسيم النص العربي لجمل، فـ الدرجات بتتكتب لكل لغة لوحدها ومش بتتجمع.

5. Our scorecard and ablations5. كارت التقييم بتاعنا والـ ablations

"There is no universal LLM metric." For legal Q&A the scorecard is:

  1. Faithfulness (RAGAS and Jev's live claim check);
  2. Citation accuracy: cited articles ⊆ retrieved articles, and the gold article is cited;
  3. Retrieval hit@5: the gold article is in the top 5;
  4. Correct refusal rate on off-topic and unanswerable questions;
  5. Cost and latency per answer (p95, TTFT, tokens).

An ablation changes one thing and re-runs the set: decider none vs local vs Jev; top-k 3/5/8; bge-m3 vs e5. If a metric never moves, it measures nothing. The best configuration wins on numbers, not opinion.

"مفيش مقياس واحد ينفع لكل تطبيقات الـ LLM." للسؤال والجواب القانوني الكارت بتاعنا:

  1. Faithfulness (من RAGAS ومن فحص Jev اللحظي للجمل)؛
  2. دقة الاستشهاد: المواد المذكورة لازم تكون من المواد اللي رجعت، والمادة الصح لازم تتذكر؛
  3. Retrieval hit@5: المادة الصح موجودة في أول 5؛
  4. نسبة الرفض الصح للأسئلة اللي بره الموضوع أو ملهاش إجابة؛
  5. التكلفة والوقت لكل إجابة (p95 وTTFT والـ tokens).

الـ ablation إنك تغيّر حاجة واحدة وتعيد التجربة: من غير decider / محلي / Jev؛ top-k بـ 3 أو 5 أو 8؛ bge-m3 قصاد e5. لو مقياس عمره ما اتحرك، يبقى مش بيقيس حاجة. وأحسن config بيكسب بالأرقام مش بالرأي.

6. Experiment tracking with MLflow6. تتبع التجارب بـ MLflow

Instead of model_v2_final_REAL.pkl and a spreadsheet, every experiment is a run in MLflow. Vocabulary: an experiment is one problem (legal-rag-retrieval); a run is one execution; params are inputs; metrics are results; artifacts are files; tags are labels for searching.

What a RAG run logs:

  • params: chunking strategy, embedding model, top-k, reranker/decider, thresholds, prompt version, LLM and judge model;
  • metrics: the four RAGAS scores per language, hit@5, citation accuracy, refusal rate, p95 latency, tokens and cost;
  • artifacts: rag_config.json, per-question results table, the prompt text;
  • tags: git_sha, dvc_data_hash, index_version.

We run MLflow the way companies do: a tracking server with Postgres for metadata and MinIO (S3-compatible) for artifacts. "MLflow won't pick your best model for you": you sort, compare and decide.

بدل model_v2_final_REAL.pkl وشيت إكسل، كل تجربة بتبقى run في MLflow. المصطلحات: الـ experiment مشكلة واحدة (legal-rag-retrieval)؛ الـ run تشغيلة واحدة؛ الـ params المدخلات؛ الـ metrics النتايج؛ الـ artifacts الفايلات؛ والـ tags علامات للبحث.

الـ run بتاع الـ RAG بيسجل:

  • params: طريقة التقسيم، موديل الـ embedding، الـ top-k، الـ reranker/decider، الحدود، نسخة الـ prompt، وموديل الكتابة والحَكَم؛
  • metrics: درجات RAGAS الأربعة لكل لغة، وhit@5، ودقة الاستشهاد، ونسبة الرفض، وp95، والـ tokens والتكلفة؛
  • artifacts: rag_config.json، وجدول نتايج كل سؤال، ونص الـ prompt؛
  • tags: git_sha وdvc_data_hash وindex_version.

بنشغّل MLflow زي الشركات: tracking server ومعاه Postgres للـ metadata وMinIO (متوافق مع S3) للـ artifacts. "MLflow مش هيختارلك أحسن موديل": إنت اللي بترتب وتقارن وتقرر.

7. The registry for a RAG system7. الـ Registry في سيستم RAG

In the course, the registry held a trained model and the API loaded models:/Name@production, never a file path. Swapping the production model needed no code change and no rebuild: "the single most important idea in Module 2".

In RAG the "model" is mostly configuration: prompt version, embedding model, index version, top-k, decider and thresholds. "A different prompt is a different model." So we register legal-rag-config whose artifact is rag_config.json. The API loads the version with alias production at startup. A candidate that beats production on the golden set gets alias staging automatically; moving production needs a human.

في الكورس الـ registry كان شايل موديل متدرب، والـ API بيحمّل models:/Name@production عمره ما يحمّل مسار فايل. تبديل موديل الـ production مكانش محتاج تعديل كود ولا rebuild: "أهم فكرة في الموديول التاني".

في الـ RAG "الموديل" أغلبه إعدادات: نسخة الـ prompt، وموديل الـ embedding، ونسخة الـ index، والـ top-k، والـ decider والحدود. "prompt مختلف = موديل مختلف." فبنسجّل legal-rag-config والـ artifact بتاعه rag_config.json. الـ API بيحمّل النسخة اللي عليها alias اسمه production وهو بيقوم. أي نسخة مرشحة تغلب الـ production على الأسئلة الذهبية بتاخد alias staging لوحدها؛ لكن نقل production محتاج بني آدم.

8. Data versioning with DVC8. إصدارات الداتا بـ DVC

Git is bad at large or binary files. DVC stores a tiny pointer file in Git (an MD5 hash + size) and the real bytes in a remote (our MinIO bucket). Storage is content-addressed: a file with the same hash is stored once, so adding one new document does not copy the old ones.

dvc add data/raw/egyptian_civil_code.pdf   # creates the .dvc pointer
dvc push                                   # upload bytes to MinIO
git checkout v0.1.0 && dvc checkout        # go back in time: code AND data

A pipeline in dvc.yaml lists stages with their command, inputs and outputs: parse → validate → index → evaluate. dvc repro re-runs only stages whose inputs changed. "A new law is passed → dvc add → dvc repro rebuilds the index."

Lineage answers "how did I get this result?": git commit → DVC data hash → MLflow run → registry version. Every run is tagged with the first two.

Git وحش مع الفايلات الكبيرة أو الـ binary. DVC بيحط فايل صغير في Git بيشاور على الداتا (MD5 hash والحجم)، والداتا نفسها في remote (bucket في MinIO). والتخزين بالمحتوى: الفايل اللي ليه نفس الـ hash بيتخزن مرة واحدة، فلو زودنا مستند جديد القديم مش بيتنسخ تاني.

الـ pipeline في dvc.yaml بيحدد المراحل وأمر كل مرحلة ومدخلاتها ومخرجاتها: parse ← validate ← index ← evaluate. وdvc repro بيعيد تشغيل المراحل اللي مدخلاتها اتغيرت بس. "نزل قانون جديد ← dvc add ← dvc repro يبني الـ index من تاني."

الـ Lineage بيجاوب على "أنا وصلت للنتيجة دي إزاي؟": git commit ← DVC data hash ← MLflow run ← نسخة الـ registry. وكل run عليه tag بأول حلقتين.

9. Prompt versioning9. إصدارات الـ prompt

The instructor's own story: her team tried many prompts, kept the best, and lost the history they needed to improve it. Prompts are code-like config and need versions.

  • Phases 2–4: prompts live in the repo with a version string; MLflow logs the version and text with every run.
  • Phase 5: the serving prompt moves to Langfuse prompt management with labels production and canary. Every trace records which version produced it, and a rollback is moving a label, which takes seconds and needs no deploy.

حكاية المهندسة نفسها: الفريق بتاعها جرّب prompts كتير، وخد الأحسن، وضاع منهم التاريخ اللي كانوا محتاجينه عشان يحسنوه. الـ prompts إعدادات زي الكود ومحتاجة versions.

  • من المرحلة 2 لـ 4: الـ prompts في الريبو بـ version؛ وMLflow بيسجل النسخة والنص مع كل run.
  • المرحلة 5: prompt الـ serving بيتنقل لـ Langfuse prompt management بـ labels production وcanary. كل trace بيسجل أنهي نسخة طلّعته، والـ rollback نقل label بياخد ثواني ومن غير deploy.

10. CI with GitHub Actions10. الـ CI بـ GitHub Actions

A team lead with 20 developers cannot review every change by hand; CI enforces the standards automatically. Building blocks: a workflow (YAML in .github/workflows/) is triggered by an event (pull request, push, schedule, manual), runs jobs on runners, and each job has steps that either uses a ready action or runs a shell command.

Our pipeline on every pull request:

lintruff, pre-commit
→
testpytest, coverage ≥ 80%
→
quality gate10 golden questions, faithfulness ≥ threshold
→
build & pushimage tagged with git SHA

A metric regression turns the check red and branch protection blocks the merge: "a CI pipeline with no failing condition is a green checkmark that means nothing." Secrets (OpenRouter key, Docker Hub token) live in GitHub Secrets, never in YAML. "Never echo a secret."

الـ team lead اللي معاه 20 مطور مش هيقدر يراجع كل تغيير بإيده؛ الـ CI بيفرض القواعد لوحده. المكونات: الـ workflow (ملف YAML في .github/workflows/) بيشتغل مع event (pull request، push، جدول مواعيد، يدوي)، ويشغّل jobs على runners، وكل job فيه steps يا إما uses action جاهزة يا إما run أمر shell.

الـ pipeline بتاعنا مع كل pull request موضح في الرسمة.

لو مقياس الجودة نزل، الفحص يبقى أحمر والـ branch protection يمنع الـ merge: "CI مفيهوش شرط فشل هو علامة صح خضرا ملهاش معنى." والأسرار (مفتاح OpenRouter وتوكن Docker Hub) في GitHub Secrets، عمرها ما تتكتب في الـ YAML. "عمرك ما تطبع secret."

11. Continuous training, RAG style11. الـ Continuous training بطريقة الـ RAG

We do not train weights, but the same loop applies: rebuild → evaluate → compare with production → promote only if better. Software CI/CD is code → test → build → deploy; ML adds training, evaluation and comparison.

إحنا مش بندرّب أوزان، بس نفس الدورة بتنطبق: نبني تاني ← نقيّم ← نقارن بالـ production ← نرقّي بس لو أحسن. الـ CI/CD بتاع السوفتوير: كود ← test ← build ← deploy؛ والـ ML بيزود التدريب والتقييم والمقارنة.

Never auto-promote to production. Staging is automatic; production needs a person to approve a GitHub Environment. Otherwise a silently broken index ships on a Friday. And not every drift alert means rebuild: a guard enforces a cooldown, a minimum amount of new evidence, and a daily cap ("retraining storms").

عمرك ما ترقّي للـ production أوتوماتيك. الـ staging أوتوماتيك؛ لكن الـ production محتاج شخص يوافق على GitHub Environment. وإلا index بايظ في صمت هينزل يوم الجمعة. ومش كل alert بـ drift معناه rebuild: فيه حماية بتفرض فترة تهدئة، وحد أدنى من الأدلة الجديدة، وحد أقصى في اليوم (عشان "عواصف إعادة التدريب").

12. Orchestration with Airflow12. التنسيق بـ Airflow

"A cron job in a file is not a pipeline. A DAG is." A DAG (directed acyclic graph) is a set of tasks with one-way dependencies and no loops. Airflow schedules it, retries failed tasks, keeps history, and shows it in a UI.

  • Operators are task types (PythonOperator, BashOperator); BranchPythonOperator chooses a path (promote or skip).
  • Sensors wait for something (a new PDF version in the bucket).
  • XCom passes small values between tasks: pass the MLflow run_id, never a DataFrame.
  • Retries and timeouts on every task; tasks are small and idempotent, so running twice for the same date does not break anything.

Division of labour: Airflow runs data and evaluation work on a schedule (re-index, nightly drift checks). GitHub Actions runs code work on repository events (tests, builds, releases). Each tool does what it is built for.

"cron job في فايل مش pipeline. الـ DAG هو الـ pipeline." الـ DAG مجموعة tasks بينهم اعتماديات في اتجاه واحد ومن غير دواير. Airflow بيجدوله، ويعيد الـ tasks اللي فشلت، ويحفظ التاريخ، ويعرضه في واجهة.

  • الـ Operators أنواع الـ tasks (PythonOperator وBashOperator)؛ والـ BranchPythonOperator بيختار طريق (نرقّي ولا نعدّي).
  • الـ Sensors بتستنى حاجة (نسخة PDF جديدة في الـ bucket).
  • الـ XCom بينقل قيم صغيرة بين الـ tasks: ابعت run_id بتاع MLflow، عمرك ما تبعت DataFrame.
  • Retries وtimeouts على كل task؛ والـ tasks صغيرة وidempotent، يعني لو اشتغلت مرتين لنفس اليوم مفيش حاجة تبوظ.

تقسيم الشغل: Airflow بيشغّل شغل الداتا والتقييم بجدول (re-index وفحص الـ drift كل ليلة). وGitHub Actions بيشغّل شغل الكود مع أحداث الريبو (tests وbuilds وreleases). كل أداة بتعمل اللي اتعملت عشانه.

13. Infrastructure as code with Terraform13. البنية التحتية ككود بـ Terraform

Clicking resources together in a console cannot be reviewed or repeated. Terraform describes infrastructure in files: a provider (AWS, or here the Docker provider), resources (the MinIO bucket container, the Postgres container, a network, volumes), and a state file recording what exists. The loop is init → fmt → validate → plan → apply, and destroy then apply must rebuild a working environment in one command.

The state file can contain secrets, so it is never committed; teams keep it in a remote backend (an S3 bucket with locking). We use the Docker provider because no cloud account is needed; the concepts transfer one-to-one to AWS.

إنك تعمل الحاجات بالكليك في console مينفعش يتراجع ولا يتكرر. Terraform بيوصف البنية التحتية في فايلات: provider (AWS، أو هنا الـ Docker provider)، وresources (container الـ MinIO، container الـ Postgres، شبكة، volumes)، وفايل state بيسجل إيه الموجود. الدورة init ← fmt ← validate ← plan ← apply، ولازم destroy وبعدها apply يرجّعوا بيئة شغالة بأمر واحد.

فايل الـ state ممكن يبقى فيه أسرار، فعمره ما يتعمله commit؛ الفرق بتحطه في remote backend (bucket على S3 بـ locking). وإحنا بنستخدم Docker provider لأن مش محتاجين حساب cloud؛ والمفاهيم نفسها بالظبط على AWS.
