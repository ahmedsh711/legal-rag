1. Inference patterns: online, batch, streaming1. أنماط الـ inference: أونلاين، batch، streaming

"The most expensive ML mistake is deploying a good model the wrong way." The question to ask first: when does the business need the prediction?

  • Online (web service): the user waits for the answer. Needs low latency.
  • Batch: compute ahead of time on a schedule; cheapest per item.
  • Streaming: react to events within seconds through a queue (Kafka, Redis Streams).

Three failure modes: cost blowout (a live API for a nightly job), SLA breach (a nightly job for something users wait on), over-engineering (Kafka for a weekly report).

"أغلى غلطة في الـ ML إنك تنزّل موديل كويس بالطريقة الغلط." أول سؤال: الـ business محتاج الـ prediction إمتى؟

  • أونلاين (web service): المستخدم مستني الإجابة. محتاج latency قليلة.
  • Batch: بنحسب بدري بجدول مواعيد؛ الأرخص للحاجة الواحدة.
  • Streaming: بنرد على أحداث في ثواني عن طريق طابور (Kafka، Redis Streams).

تلات طرق للفشل: التكلفة تنفجر (API لايف لشغلانة بتتعمل بالليل)، الـ SLA يتكسر (شغلانة بالليل لحاجة الناس مستنياها)، تعقيد زيادة (Kafka لتقرير أسبوعي).

2. Serving vocabulary and the layers of a serving stack2. مصطلحات الـ serving وطبقاته

"Inference is a function call. Serving is everything you build around it." Words you must use precisely:

  • Latency (time per request) vs throughput (requests per second). A fast request does not mean a fast system.
  • p50 / p95 / p99: the time under which 50/95/99% of requests finish. "The average lies; p99 breaks your SLA."
  • Cold start: the first request after a start, while models load.
  • TTFT and TBT (time between tokens, target under about 50 ms) for LLMs.

Four layers: L1 transport/API, L2 scheduling (batching, queues, versions), L3 inference runtime, L4 hardware. FastAPI owns L1; BentoML L1+L2; Triton L1–L3; vLLM L1–L3 for LLMs. "Move to a heavier category only with a measured reason, never 'Triton will be faster'."

In this project: FastAPI is the application (auth, validation, pipeline, streaming); vLLM serves the local LLM; BentoML wraps the same pipeline in Phase 4 to show adaptive batching and its built-in health and metrics endpoints, and the Locust numbers decide which we keep.

"الـ Inference مجرد function call. الـ Serving هو كل اللي بتبنيه حواليه." كلمات لازم تستخدمها بدقة:

  • Latency (وقت الطلب الواحد) قصاد throughput (طلبات في الثانية). الطلب السريع مش معناه سيستم سريع.
  • p50 / p95 / p99: الوقت اللي 50/95/99% من الطلبات بتخلص قبله. "المتوسط بيكدب؛ وp99 هو اللي بيكسر الـ SLA."
  • Cold start: أول طلب بعد التشغيل، والموديلات لسه بتتحمل.
  • TTFT وTBT (الوقت بين كل token واللي بعده، المستهدف أقل من 50 ملي ثانية تقريبًا) في الـ LLMs.

أربع طبقات: L1 النقل والـ API، L2 الجدولة (batching وطوابير وversions)، L3 الـ runtime، L4 الهاردوير. FastAPI بيمسك L1؛ BentoML بيمسك L1 وL2؛ Triton من L1 لـ L3؛ وvLLM من L1 لـ L3 للـ LLMs. "متنقلش لفئة أتقل غير بسبب متقاس بأرقام، عمرك ما تقول Triton هيبقى أسرع."

في مشروعنا: FastAPI هو التطبيق (الصلاحيات والـ validation والـ pipeline والـ streaming)؛ وvLLM بيخدّم الـ LLM المحلي؛ وBentoML بيلف نفس الـ pipeline في المرحلة 4 عشان نشوف الـ batching والـ endpoints الجاهزة للـ health والـ metrics، وأرقام Locust هي اللي تقرر نسيب مين.

3. Load testing with Locust3. اختبار الحمل بـ Locust

A load test finds the maximum requests per second, the p50/p95/p99 at each load, the saturation point (where p95 starts climbing steeply), and which component breaks first. "1,000 users is not 1,000 requests per second": users think between requests.

  • Realistic traffic: a mix of Arabic and English questions, some streamed, some metadata calls, random waits. Sending the same question 10,000 times makes every cache lie.
  • LLM-specific: measure TTFT under concurrency and test at the realistic (p95) question length.
  • Diagnose with evidence: CPU-bound, memory-bound, I/O-bound (waiting on OpenRouter/Jev), or queue-bound. Change one parameter, re-run, compare.

Honest limit: the load generator and the service share one laptop, so we measure the laptop too. The report says so.

اختبار الحمل بيطلّع أقصى عدد طلبات في الثانية، وp50/p95/p99 عند كل حمل، ونقطة التشبع (لما p95 يبدأ يطلع بسرعة)، وأنهي جزء بيقع الأول. "1,000 مستخدم مش يعني 1,000 طلب في الثانية": المستخدمين بيفكروا بين كل طلب والتاني.

  • ترافيك واقعي: أسئلة عربي وإنجليزي مخلوطة، شوية streaming، شوية نداءات metadata، وانتظار عشوائي. لو بعت نفس السؤال 10,000 مرة كل cache هيكدب عليك.
  • خاص بالـ LLM: نقيس TTFT مع الضغط، ونختبر بطول سؤال واقعي (p95).
  • تشخيص بدليل: المشكلة في الـ CPU، ولا الذاكرة، ولا انتظار I/O (OpenRouter وJev)، ولا طابور. نغيّر parameter واحد ونعيد ونقارن.

حد بصراحة: مولّد الحمل والخدمة على نفس اللابتوب، فإحنا بنقيس اللابتوب كمان. والتقرير بيقول كده.

4. Release strategies4. طرق نزول نسخة جديدة

Deploying (starting new containers) is separate from routing traffic to them. "Test → Monitor → Gradual rollout → Roll back if needed", not "Deploy → Pray".

الـ deploy (تشغيل containers جديدة) حاجة، وتوجيه الترافيك ليها حاجة تانية. "اختبر ← راقب ← نزّل بالتدريج ← ارجع لو احتجت"، مش "نزّل وادعي".

In this project: nginx sends 95/5 traffic to stable/canary API containers and tags every response with the serving version; promote.sh ramps the weight; rollback.sh returns to 100% stable in one command (and we time it); a watcher reads Prometheus and rolls back automatically if canary p95 or errors break the SLA twice in a row; nginx mirror gives shadow mode. Two cheaper rollbacks exist too: moving the Qdrant alias (index) and moving the Langfuse label (prompt).

في مشروعنا: nginx بيبعت 95/5 من الترافيك للنسخة المستقرة والـ canary، وكل رد عليه اسم النسخة اللي ردت؛ promote.sh بيزود النسبة؛ rollback.sh بيرجّع 100% للمستقرة بأمر واحد (وبنقيس وقته)؛ وفيه watcher بيقرا Prometheus ويعمل rollback لوحده لو p95 أو الأخطاء في الـ canary كسروا الـ SLA مرتين ورا بعض؛ وnginx mirror بيدينا الـ shadow mode. وفيه طريقتين rollback أرخص: نرجّع الـ alias في Qdrant (للـ index) ونرجّع الـ label في Langfuse (للـ prompt).

5. Kubernetes essentials5. أساسيات Kubernetes

  • Pod: one or more containers scheduled together. Deployment: keeps N identical pods running and handles rolling updates. Service: a stable address that load-balances to pods selected by labels. Ingress: routes outside HTTP traffic to services (and does canary weights with NGINX annotations).
  • Labels are the routing contract (app, version, track: stable|canary); services select pods by labels, not names.
  • Probes: liveness (restart if dead), readiness (send traffic only when ready), startup (still loading).
  • Requests/limits reserve and cap CPU/memory. ConfigMap holds config; Secret holds secrets, but "Secrets are base64-encoded, not encrypted".
  • kubectl rollout status, rollout undo, get events are the release checklist.

We write real manifests and apply them to Docker Desktop's built-in Kubernetes. The course calls full Kubernetes operations "advanced"; we learn the objects and the rollout, not cluster administration.

  • Pod: container أو أكتر بيتشغلوا مع بعض. Deployment: بيحافظ إن فيه N pods شبه بعض شغالين وبيعمل الـ rolling updates. Service: عنوان ثابت بيوزّع على الـ pods اللي بيختارها بالـ labels. Ingress: بيوجّه الترافيك اللي جاي من بره للـ services (وبيعمل نسب الـ canary بـ annotations في NGINX).
  • الـ labels هي عقد التوجيه (app وversion وtrack: stable|canary)؛ الـ service بيختار الـ pods بالـ labels مش بالأسماء.
  • Probes: liveness (لو ميت اعمل restart)، readiness (ابعت ترافيك بس لما يبقى جاهز)، startup (لسه بيحمّل).
  • Requests/limits بتحجز وبتحد الـ CPU والذاكرة. ConfigMap للإعدادات؛ Secret للأسرار، بس "الـ Secrets بتتعمل base64 مش تشفير".
  • kubectl rollout status وrollout undo وget events هما checklist النزول.

هنكتب manifests حقيقية ونطبقها على Kubernetes اللي جوه Docker Desktop. الكورس بيعتبر تشغيل Kubernetes الكامل "متقدم"؛ إحنا بنتعلم الـ objects والـ rollout، مش إدارة الكلاستر.

6. Monitoring tiers and the three pillars6. مستويات المراقبة والأعمدة التلاتة

You cannot watch everything, so decide what you watch when:

  • Watch now (every request, seconds): request rate, errors, p95, TTFT, tokens, refusals, gate probabilities.
  • Watch today (scheduled, no labels): drift of questions against a frozen reference, distribution of retrieval scores, RAGAS on a 1–5% sample.
  • Check later (needs people): human review, golden-set regressions.

"The proxies are your alarm. The labels are your audit."

The three pillars: metrics answer "is something wrong right now, and how big?"; logs answer "what exactly happened in this request?"; traces answer "where did the time go across the steps?". The request_id joins all three.

مينفعش تراقب كل حاجة، فقرر هتراقب إيه وإمتى:

  • راقب دلوقتي (مع كل طلب، بالثواني): عدد الطلبات، والأخطاء، وp95، وTTFT، والـ tokens، والرفض، واحتمالات الـ gate.
  • راقب النهارده (بجدول، من غير labels): drift الأسئلة قصاد مرجع ثابت، وتوزيع درجات الـ retrieval، وRAGAS على عينة 1–5%.
  • اتأكد بعدين (محتاج بشر): مراجعة بشرية، وأي تراجع في الأسئلة الذهبية.

"المؤشرات هي جرس الإنذار، والـ labels هي المراجعة."

الأعمدة التلاتة: الـ metrics بتجاوب "فيه حاجة غلط دلوقتي؟ وقد إيه؟"؛ الـ logs بتجاوب "إيه اللي حصل بالظبط في الطلب ده؟"؛ والـ traces بتجاوب "الوقت راح فين بين الخطوات؟". والـ request_id بيربط التلاتة.

7. Prometheus7. Prometheus

Prometheus pulls: our API exposes /metrics and Prometheus scrapes it every 15 seconds. A target that stops answering is itself a signal. Metric types:

  • Counter: only goes up (rag_requests_total); always query its rate().
  • Gauge: goes up and down (rag_inflight_requests).
  • Histogram: counts values in buckets (rag_stage_seconds{stage}) so you can compute p95 across instances, which an average cannot.

Cardinality: each unique label combination is a separate time series. Never put user_id, request_id or question text in a label; "unbounded labels are the classic way to take down Prometheus". Those go in logs and traces. Buckets are chosen around our SLA (e.g. 0.1 s … 10 s), and units are base units: seconds, bytes.

histogram_quantile(0.95, sum(rate(rag_stage_seconds_bucket[5m])) by (le, stage))   # p95 per stage
sum(rate(rag_requests_total{status="error"}[5m])) / sum(rate(rag_requests_total[5m])) # error rate

rate() is per second, for graphs; increase() is a total over a window, for reports. With several worker processes each keeps its own counters, so we enable multiprocess mode or counters appear to go backwards. Exporters add the rest: node_exporter (host), cAdvisor (containers), blackbox (probe from outside), vLLM and Qdrant's own /metrics.

Prometheus بـ يسحب: الـ API بتاعنا بيعرض /metrics وPrometheus بيقراها كل 15 ثانية. ولو الهدف بطّل يرد، ده في حد ذاته إشارة. أنواع الـ metrics:

  • Counter: بيزيد بس (rag_requests_total)؛ ودايمًا بنستعلم عن الـ rate() بتاعه.
  • Gauge: بيطلع وينزل (rag_inflight_requests).
  • Histogram: بيعد القيم في buckets (rag_stage_seconds{stage}) فنقدر نحسب p95 على كل النسخ، والمتوسط ميقدرش.

الـ Cardinality: كل تركيبة labels مختلفة = time series لوحدها. عمرك ما تحط user_id أو request_id أو نص السؤال في label؛ "الـ labels اللي ملهاش حد هي الطريقة الكلاسيكية لوقعان Prometheus". دول مكانهم الـ logs والـ traces. والـ buckets بنختارها حوالين الـ SLA بتاعنا (مثلاً من 0.1 لـ 10 ثانية)، والوحدات أساسية: ثواني وbytes.

الـ rate() لكل ثانية، للرسومات؛ والـ increase() إجمالي في فترة، للتقارير. ولو فيه كذا worker process كل واحد بيحسب لوحده، فبنشغّل multiprocess mode وإلا الـ counters هتبان كأنها بترجع لورا. والـ Exporters بتكمّل الصورة: node_exporter (الجهاز)، cAdvisor (الـ containers)، blackbox (فحص من بره)، و/metrics بتاعة vLLM وQdrant نفسهم.

8. Grafana dashboards as code8. Dashboards في Grafana ككود

One dashboard, four rows: service health (rate, errors, p50/p95/p99, in-flight, uptime), resources (CPU, RAM, disk, GPU/VRAM, per container), RAG behaviour (stage latency, decisions by outcome, refusal rate, tokens and cost, serving version), quality and drift (faithfulness from sampled evaluation, drift scores from Postgres).

The dashboard JSON and data sources live in the repo and are provisioned at startup: "a dashboard built by clicking dies with the pod". Deploy annotations draw a line on every graph when a version ships; "half of all drift investigations end the moment you see the spike land on a release".

dashboard واحدة وأربع صفوف: صحة الخدمة (عدد الطلبات، الأخطاء، p50/p95/p99، الطلبات الشغالة، الـ uptime)، الموارد (CPU وRAM والديسك والـ GPU والـ VRAM، ولكل container)، سلوك الـ RAG (وقت كل مرحلة، القرارات ونتيجتها، نسبة الرفض، الـ tokens والتكلفة، النسخة الشغالة)، الجودة والـ drift (faithfulness من التقييم بالعينة، ودرجات الـ drift من Postgres).

ملف الـ dashboard JSON والـ data sources في الريبو وبيتعملهم provisioning وقت التشغيل: "الـ dashboard اللي اتعملت بالكليك بتموت مع الـ pod". والـ deploy annotations بترسم خط على كل رسمة لما نسخة تنزل؛ "نص تحقيقات الـ drift بتخلص أول ما تشوف الارتفاع جه مع release".

9. Alerting people trust9. Alerts الناس تثق فيها

Page on symptoms, ticket on causes. Symptoms are what users feel (service down, p95 above SLA, error rate above 1%, faithfulness below 0.80). Causes hurt later (drift score, VRAM near full, token budget burning fast, index older than allowed).

  • Every rule has for: (e.g. 5 minutes) so one scrape blip never pages anyone.
  • Alertmanager routes by severity (page channel vs ticket channel), groups related alerts, and inhibits the latency alert while "service down" is firing. One incident, one notification.
  • Every alert's text has an obvious first action and a link to its runbook section. "drift detected" alone gets muted by week two.
  • An SLO burn-rate alert uses two windows: the short one catches fast burns, the long one filters noise.

صحّي الناس على الأعراض، وافتح تذكرة على الأسباب. الأعراض هي اللي المستخدم بيحس بيها (الخدمة واقعة، p95 فوق الـ SLA، الأخطاء فوق 1%، الـ faithfulness تحت 0.80). والأسباب بتأذي بعدين (درجة drift، الـ VRAM قرب يتملي، ميزانية الـ tokens بتخلص بسرعة، الـ index أقدم من المسموح).

  • كل قاعدة فيها for: (مثلاً 5 دقايق) عشان غلطة scrape واحدة متصحّيش حد.
  • Alertmanager بيوجّه حسب الخطورة (قناة طوارئ قصاد قناة تذاكر)، ويجمّع الـ alerts اللي ليها علاقة ببعض، ويكتم alert الـ latency طول ما "الخدمة واقعة" شغال. مشكلة واحدة، إشعار واحد.
  • نص كل alert فيه أول خطوة واضحة ولينك لجزء الـ runbook بتاعه. "فيه drift" لوحدها هتتكتم بعد أسبوعين.
  • alert الـ SLO burn-rate بيستخدم نافذتين: القصيرة بتمسك الاستهلاك السريع، والطويلة بتصفّي الدوشة.

10. Drift: quality drops without an error10. الـ Drift: الجودة بتقل من غير error

Classic drift types: data (inputs change), concept (the right answer for the same input changes; for us, a law amendment), prediction (output distribution moves), label (class mix changes). RAG adds four:

  • Embedding drift: the index and the query encoder differ. Signals: zero-hit rate, mean top-1 similarity. Guard: refuse to start on mismatch.
  • Corpus drift: documents changed but the index did not, or repealed text is still served. Signals: index vs source count, age of cited articles.
  • Retrieval drift: a few articles dominate every answer, similarity decays. Signals: mean top-k similarity, concentration of reused articles, context precision by week.
  • Query-intent drift: users start asking about something else (family law, criminal law). Signals: refusal rate, off-topic rate, embedding-based detectors.

LLM apps add provider drift (same model name, different model: pin versions, run the golden set weekly), prompt drift ("a hundred small edits"), and evaluator drift (pin the judge).

"Drift does not automatically mean the model is broken." Check in order: an upstream bug ("most drift is this"), seasonality, real user change, and only then rebuild.

أنواع الـ drift الكلاسيكية: data (المدخلات بتتغير)، concept (الإجابة الصح لنفس المدخل بتتغير؛ عندنا: تعديل في القانون)، prediction (توزيع المخرجات بيتحرك)، label (نسب الأصناف بتتغير). والـ RAG بيزود أربعة:

  • Embedding drift: الـ index وencoder الأسئلة مختلفين. الإشارات: نسبة البحث اللي مرجّعش حاجة، ومتوسط تشابه أول نتيجة. الحماية: نرفض نقوم لو مش متطابقين.
  • Corpus drift: المستندات اتغيرت والـ index لأ، أو نص ملغي لسه بيتخدّم. الإشارات: عدد الـ index قصاد المصدر، وعمر المواد المذكورة.
  • Retrieval drift: شوية مواد بيسيطروا على كل الإجابات، والتشابه بيقل. الإشارات: متوسط تشابه أول k، وتركيز المواد المتكررة، والـ context precision كل أسبوع.
  • Query-intent drift: الناس بدأت تسأل عن حاجة تانية (أحوال شخصية، جنائي). الإشارات: نسبة الرفض، ونسبة الأسئلة اللي بره الموضوع، وكواشف مبنية على الـ embeddings.

وتطبيقات الـ LLM بتزود provider drift (نفس اسم الموديل بس موديل مختلف: ثبّت النسخ وشغّل الأسئلة الذهبية كل أسبوع)، وprompt drift ("مية تعديل صغير")، وevaluator drift (ثبّت الحَكَم).

"الـ Drift مش معناه تلقائيًا إن الموديل باظ." اتأكد بالترتيب: bug في حاجة قبلنا ("أغلب الـ drift كده")، موسمية، تغيير حقيقي عند المستخدمين، وبعدين بس نعيد البناء.

Every detector must stay silent on an undrifted control set; "a detector with no measured false-positive rate is not a detector". 11. Drift reports and where they are stored11. تقارير الـ drift وبتتخزن فين

Evidently compares this window's data with a frozen reference (never roll the baseline forward). A Report is for humans; a Test suite with explicit conditions is for machines, so only tests can be a CI gate. Evidently's API changed at version 0.7, so we pin the version and read the current docs, not old blog posts.

A daily job writes one row per window, metric and feature into a Postgres table (drift_metrics). Prometheus is the wrong store for a number computed once a day and kept for a year; Postgres is right, and Grafana reads it with a SQL data source. When drift passes the threshold and the guards allow it, the Airflow branch triggers re-index and re-evaluation; a human still approves production.

Evidently بيقارن داتا الفترة دي بـ مرجع ثابت (عمرك ما تحرّك المرجع لقدام). الـ Report للبشر؛ والـ Test suite بشروط واضحة للماكينات، فالـ tests بس هي اللي تنفع بوابة في الـ CI. والـ API بتاع Evidently اتغير من نسخة 0.7، فبنثبت النسخة ونقرا الـ docs الحالية مش بوستات قديمة.

شغلانة يومية بتكتب صف لكل فترة ومقياس وخاصية في جدول Postgres اسمه drift_metrics. Prometheus مش المكان الصح لرقم بيتحسب مرة في اليوم ونحتفظ بيه سنة؛ Postgres هو الصح، وGrafana بيقراه بـ SQL. ولما الـ drift يعدي الحد والحمايات تسمح، فرع في Airflow بيشغّل re-index وتقييم من جديد؛ وبرضه بني آدم هو اللي يوافق على الـ production.

12. LLM observability with Langfuse12. مراقبة الـ LLM بـ Langfuse

Langfuse answers three questions: what happened (tracing), which version produced it (prompt management), and was it good (scores). Its objects:

  • Trace: one question, end to end, with user_id, session_id, release and tags.
  • Observations inside it: spans (route, retrieve, rerank, gate, validate), generations (an LLM call with tokens and cost), events.
  • Scores attached afterwards: gate probability, supported-claim ratio, RAGAS faithfulness, user feedback.
  • Datasets: the golden set, run as experiments and compared item by item.

Every trace carries the same metadata as our logs: request_id, prompt version, index version, top-k, decider. Test: can you list every answer that made a legal claim with zero retrieved articles in under a minute? Cost is tracked per trace, including a custom price for our own vLLM (from GPU hourly price ÷ measured throughput). Langfuse is self-hosted (web, worker, Postgres, ClickHouse, Redis, MinIO) so legal questions never leave our infrastructure.

Langfuse بيجاوب على تلات أسئلة: إيه اللي حصل (tracing)، وأنهي نسخة طلّعته (إدارة الـ prompts)، وكان كويس ولا لأ (scores). الـ objects بتاعته:

  • Trace: سؤال واحد من أوله لآخره، ومعاه user_id وsession_id والـ release والـ tags.
  • Observations جواه: spans (route وretrieve وrerank وgate وvalidate)، وgenerations (نداء LLM بالـ tokens والتكلفة)، وevents.
  • Scores بتتضاف بعدين: احتمال الـ gate، ونسبة الجمل اللي ليها دليل، وfaithfulness من RAGAS، ورأي المستخدم.
  • Datasets: الأسئلة الذهبية، بتتشغل كتجارب ونقارن سؤال سؤال.

كل trace شايل نفس الـ metadata اللي في الـ logs: request_id ونسخة الـ prompt ونسخة الـ index والـ top-k والـ decider. الاختبار: تقدر تطلّع كل إجابة قالت معلومة قانونية من غير ولا مادة راجعة في أقل من دقيقة؟ والتكلفة بتتحسب لكل trace، حتى سعر vLLM بتاعنا (سعر ساعة الـ GPU ÷ الـ throughput المتقاس). وLangfuse متشغّل عندنا (web وworker وPostgres وClickHouse وRedis وMinIO) فالأسئلة القانونية عمرها ما تخرج بره البنية بتاعتنا.

13. Optimization and cost13. الـ Optimization والتكلفة

"An unmeasured optimization is a rumour." Before optimizing we state one objective and one constraint (for example: minimize p95 subject to faithfulness drop ≤ 0.03), and build a benchmark harness with warm-up runs, enough repetitions, the same evaluation set every time, and a hardware column, because a laptop CPU number must never sit next to a cloud GPU number unlabelled.

Where RAG cost really goes, usually in this order: too much context (top-k too high), a model bigger than the task needs, and retry loops. Levers: fewer, better chunks (rerank + gate); a quantized local model (AWQ 4-bit) for easy questions; caching repeated questions; exporting the CPU reranker to ONNX if it is the bottleneck. Every row of the final table gets an accuracy column and a cost per month at a stated traffic level.

The honesty clause: "I tried X, quality dropped 4%, so I shipped Y" scores higher than a flawless table with no accuracy column. Fabricated numbers fail the project outright.

"الـ optimization اللي متقاسش إشاعة." قبل ما نحسّن بنحدد هدف واحد وقيد واحد (مثلاً: قلّل p95 بشرط الـ faithfulness ميقلش أكتر من 0.03)، ونبني أداة قياس فيها تسخين قبل القياس، وتكرار كفاية، ونفس أسئلة التقييم كل مرة، وعمود للهاردوير، لأن رقم CPU لابتوب عمره ما يتحط جنب رقم GPU سحابي من غير ما نوضح.

تكلفة الـ RAG بتروح فين فعلاً، غالبًا بالترتيب ده: context كتير (top-k عالي)، وموديل أكبر من اللازم، وloops إعادة المحاولة. الأدوات: chunks أقل وأحسن (rerank وgate)؛ موديل محلي مضغوط (AWQ 4-bit) للأسئلة السهلة؛ cache للأسئلة المتكررة؛ وتصدير الـ reranker لـ ONNX لو هو اللي معطّل الـ CPU. وكل صف في الجدول النهائي فيه عمود دقة وتكلفة شهرية عند ترافيك محدد.

شرط الأمانة: "جربت X والجودة قلت 4% فنزّلت Y" بتاخد درجة أعلى من جدول مثالي مفيهوش عمود دقة. والأرقام المتألفة بتسقّط المشروع على طول.

14. Runbooks and incidents14. الـ Runbooks والحوادث

A runbook lets an on-call engineer who has never seen the code act at 3 am. One section per alert: what it means in one sentence, the first command to run, how to tell a real problem from a data-pipeline failure, the rollback command, and when to escalate. "An alert without a runbook is noise."

The instructor's degraded-model runbook: is it the model at all? → the data pipeline → the deploy timeline (roll back first, investigate second) → localize → check real quality → decide and write it down. Incidents are written in five sentences: context, signal, action, outcome, lesson. Across every real incident she showed, "the model was never the root cause", and the missing signal was always cheap.

الـ runbook بيخلي المهندس المناوب، اللي عمره ما شاف الكود، يتصرف الساعة 3 الفجر. جزء لكل alert: معناه في جملة، أول أمر يشغّله، يفرّق إزاي بين مشكلة حقيقية وعطل في pipeline الداتا، أمر الـ rollback، وإمتى يصعّد. "alert من غير runbook دوشة."

الـ runbook بتاع المهندسة لما الموديل يسوء: هو الموديل أصلاً؟ ← pipeline الداتا ← تاريخ الـ deploys (ارجع الأول، وحقق بعدين) ← حدد المكان ← اتأكد من الجودة الحقيقية ← قرر واكتب اللي حصل. والحوادث بتتكتب في خمس جمل: السياق، الإشارة، اللي عملناه، النتيجة، الدرس. وفي كل الحوادث الحقيقية اللي عرضتها، "الموديل عمره ما كان السبب"، والإشارة اللي كانت ناقصة كانت دايمًا رخيصة.
