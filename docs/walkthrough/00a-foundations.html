1. What MLOps is1. يعني إيه MLOps

You train a model in a notebook and it works on your laptop. MLOps is everything needed so that it also works for other people, every day, and you can prove what it did: packaging, versioning code and data, automated tests, deployment, monitoring, and safe updates.

  • DevOps ships software reliably: build, test, deploy.
  • DataOps moves data reliably from source to consumers.
  • MLOps joins both and adds what is special to models: experiments, model versions, retraining, drift.
  • LLMOps is MLOps for LLM apps. Same ideas, plus prompts, tokens and cost, traces, LLM judges, and new kinds of drift (the provider changes the model, someone edits the prompt).

The instructor's opening point: most teams already "do MLOps", badly. Models sent over WhatsApp, files named model_final_final.pkl, notebooks nobody else can run.

إنت بتدرّب موديل في نوتبوك وبيشتغل على اللابتوب بتاعك. الـ MLOps هو كل اللي محتاجه عشان يشتغل لناس تانية، كل يوم، وتقدر تثبت هو عمل إيه: packaging، وversions للكود والداتا، وtests أوتوماتيك، وdeployment، ومراقبة، وتحديثات آمنة.

  • DevOps: إنك تنزّل سوفتوير بشكل موثوق: build وtest وdeploy.
  • DataOps: إن الداتا توصل من مصدرها للي محتاجها بشكل موثوق.
  • MLOps: بيجمع الاتنين ويزود الحاجات الخاصة بالموديلات: التجارب، وversions الموديل، وإعادة التدريب، والـ drift.
  • LLMOps: هو MLOps لتطبيقات الـ LLM. نفس الأفكار، وزيادة عليها الـ prompts، والـ tokens والتكلفة، والـ traces، والـ judges، وأنواع drift جديدة (الـ provider يغيّر الموديل، حد يعدّل الـ prompt).

أول نقطة قالتها المهندسة آية: أغلب الفرق "بتعمل MLOps" أصلاً، بس غلط. موديلات بتتبعت على الواتساب، وفايلات اسمها model_final_final.pkl، ونوتبوكات محدش غيرك يعرف يشغلها.

"I teach concepts, not tools." Tools change overnight; learn one tool per concept and stay flexible.
"أنا مش بعلّمك tool، أنا بعلّمك concept." التولز بتتغير في يوم وليلة؛ اتعلم tool واحدة لكل مفهوم وخليك مرن.

3. Repo layout and packaging3. ترتيب الريبو والـ packaging

A notebook is a pile of cells; a package is code other code can import, install and test. We use the src layout: the code lives in src/legalrag/, tests in tests/. Because tests import the installed package, they catch "works only from my folder" bugs.

pyproject.toml is the one file that describes the project: name, Python version, dependencies, dev dependencies, and tool settings (ruff, pytest, coverage). It replaced requirements.txt, which "used to get people in trouble" (no versions, conflicts).

uv creates the virtual environment, resolves versions, and writes uv.lock: the exact version of every package. Commit the lock file so every machine (yours, CI, Docker) installs the same thing.

uv sync          # create .venv and install exactly what uv.lock says
uv add httpx      # add a dependency (uv picks a compatible version)
uv run pytest    # run inside the project environment

النوتبوك كومة cells؛ لكن الـ package كود تقدر تعمله import من كود تاني، وتسطّبه، وتختبره. بنستخدم src layout: الكود في src/legalrag/ والـ tests في tests/. ولأن الـ tests بتعمل import للـ package المتسطّب، بتمسك مشاكل "شغال من الفولدر بتاعي بس".

pyproject.toml هو الفايل الوحيد اللي بيوصف المشروع: الاسم، نسخة بايثون، المكتبات، مكتبات التطوير، وإعدادات التولز (ruff وpytest وcoverage). جه بدل requirements.txt اللي "كان بيوقّع الناس في مشاكل" (من غير versions، وتعارضات).

uv بيعمل الـ virtual environment، ويحل الـ versions، ويكتب uv.lock: النسخة المظبوطة من كل مكتبة. اعمل commit للـ lock عشان كل جهاز (جهازك، الـ CI، Docker) يسطّب نفس الحاجة بالظبط.

4. Configuration and secrets4. الإعدادات والأسرار

Paths, URLs, model names and thresholds change between your laptop, CI and production. If they are written inside the code, every change is a code change. So all of them come from environment variables, with sane defaults, read in one place: src/legalrag/settings.py.

We use pydantic-settings: it reads env vars (or a local .env file), converts types, and validates ranges, so GATE_THRESHOLD=1.7 fails at startup instead of silently breaking answers.

Secrets (API keys) are typed as SecretStr, so printing the settings shows **********. They live only in .env (git-ignored) and in GitHub Secrets for CI. The instructor's warning: bots crawl public GitHub repos for keys within hours.

المسارات والـ URLs وأسماء الموديلات والحدود بتختلف بين اللابتوب والـ CI والـ production. لو مكتوبة جوه الكود، كل تغيير هيبقى تعديل كود. عشان كده كلها جاية من environment variables بقيم افتراضية معقولة، وبنقراها من مكان واحد: src/legalrag/settings.py.

بنستخدم pydantic-settings: بيقرا الـ env vars (أو فايل .env محلي)، ويحوّل الأنواع، ويتأكد من الحدود؛ فلو حد كتب GATE_THRESHOLD=1.7 البرنامج يقع وهو بيقوم بدل ما يبوّظ الإجابات في صمت.

الأسرار (API keys) نوعها SecretStr، فلو طبعت الإعدادات هتظهر **********. ومكانها .env بس (والـ git بيتجاهله) وGitHub Secrets للـ CI. وتحذير المهندسة: فيه bots بتلف على الريبوهات العامة وتلقط المفاتيح في ساعات.

5. Interfaces you can swap5. واجهات تقدر تبدّلها

In Session 1 the model sat behind a ModelBase class with one method, predict(), so swapping sklearn for XGBoost did not touch the API. This is abstraction: callers depend on what a thing does, not how.

We apply the same idea in two places where we really have two implementations:

  • Decider (abstract base class) with JevDecider and LocalDecider. The pipeline calls route(), rerank(), can_answer(), validate() and never knows which one answered.
  • The LLM client: OpenRouter or local vLLM. Both speak the same OpenAI-compatible API, so the switch is one setting, not a second class.

We do not add interfaces with only one implementation. An abstraction earns its place only when there is a real second option.

في السيشن الأولى الموديل كان ورا class اسمها ModelBase فيها method واحدة predict()، فلما تبدّل sklearn بـ XGBoost الـ API مبيتغيرش. ده اسمه abstraction: اللي بيستخدم الحاجة بيعتمد على هي بتعمل إيه مش بتعمله إزاي.

بنطبق نفس الفكرة في مكانين عندنا فيهم فعلاً اختيارين:

  • Decider (abstract base class) وتحته JevDecider وLocalDecider. الـ pipeline بينادي route() وrerank() وcan_answer() وvalidate() ومبيعرفش مين اللي جاوب.
  • الـ LLM client: OpenRouter أو vLLM محلي. الاتنين بيتكلموا نفس الـ API بتاع OpenAI، فالتبديل setting واحد مش class تانية.

ومش بنعمل interfaces ليها implementation واحدة بس. الـ abstraction بيستاهل مكانه لما يبقى فيه اختيار تاني حقيقي.

6. APIs with FastAPI6. الـ APIs باستخدام FastAPI

"An API is a remote function call." A client sends an HTTP request; our service runs the pipeline and returns JSON. Parts of a request: path (which resource, /ask), query (how, ?stream=true), body (what, the question), headers (metadata, X-Request-ID, API key). Asking a question is a POST because it carries a body.

The checklist from Session 1, mapped to our endpoints:

  1. Validate input with Pydantic: question: str = Field(min_length=3, max_length=2000). Bad input returns 422 automatically and never reaches the model or the token budget. "Never trust incoming data."
  2. Health endpoints: liveness ("is the process alive? restart me if not") and readiness ("are Qdrant and the config loaded? send me traffic"). A pod can be alive but not ready.
  3. Load once: the embedding model, the Qdrant client and the config load in FastAPI's lifespan at startup. Loading per request costs hundreds of milliseconds each time ("كارثة").
  4. Async for waiting, threads for computing: calls to Qdrant, Jev and the LLM are I/O, so async lets one worker serve many users while they wait. Embedding a query is CPU work; inside async it would freeze everyone, so it runs in run_in_threadpool. "async does NOT make CPU work faster."
  5. Response schema: response_model=AskResponse fixes the contract with clients and stops internal fields from leaking.
  6. Timeouts on every outside call: "never call an external inference service without a timeout."
  7. Streaming: /ask?stream=true sends tokens with Server-Sent Events, so the user sees the answer start fast (TTFT).
  8. Honest errors: 422 explains what is wrong; 429 says "too many requests, retry after N seconds"; 500/503 are logged with detail but never show a traceback to the client.

"الـ API ده function call من بعيد." الـ client بيبعت HTTP request؛ والخدمة بتاعتنا بتشغّل الـ pipeline وترجع JSON. أجزاء الـ request: الـ path (أنهي resource، /ask)، الـ query (إزاي، ?stream=true)، الـ body (إيه، السؤال نفسه)، والـ headers (معلومات زيادة زي X-Request-ID والـ API key). السؤال بيتبعت POST لأن معاه body.

الـ checklist من السيشن الأولى، وإزاي بنطبقها:

  1. نتأكد من المدخلات بـ Pydantic: Field(min_length=3, max_length=2000). أي مدخل غلط بيرجع 422 لوحده ومبيوصلش للموديل ولا بيصرف tokens. "متثقش أبدًا في الداتا اللي داخلة."
  2. Health endpoints: الـ liveness ("البروسيس عايشة؟ لو لأ اعملي restart") والـ readiness ("Qdrant والـ config اتحملوا؟ ابعتلي ترافيك"). ممكن تبقى عايش بس مش جاهز.
  3. حمّل مرة واحدة: موديل الـ embedding وclient الـ Qdrant والـ config بيتحملوا في الـ lifespan وقت ما السيرفر يقوم. لو حمّلتهم مع كل request هتخسر مئات الملي ثانية كل مرة ("كارثة").
  4. async للانتظار، وthreads للحساب: النداءات لـ Qdrant وJev والـ LLM كلها I/O، فالـ async بيخلي worker واحد يخدم ناس كتير وهم مستنيين. لكن الـ embedding شغل CPU؛ لو اتعمل جوه async هيجمّد الكل، فبنشغله في run_in_threadpool. "الـ async مش بيسرّع شغل الـ CPU."
  5. شكل الرد ثابت: response_model=AskResponse بيثبت العقد مع الـ client ويمنع أي حقول داخلية تطلع.
  6. timeout على كل نداء بره: "عمرك ما تنادي خدمة inference من غير timeout."
  7. Streaming: /ask?stream=true بيبعت الـ tokens بـ Server-Sent Events، فالمستخدم يشوف الإجابة بتبدأ بسرعة (TTFT).
  8. أخطاء صريحة: 422 بيقول إيه الغلط؛ 429 بيقول "طلبات كتير، جرّب تاني بعد N ثانية"؛ و500/503 بيتسجلوا بالتفاصيل بس عمر الـ traceback ما يطلع للـ client.

7. Saving models and data safely7. حفظ الموديلات والداتا بأمان

Pickle runs code when you load it. Never load a .pkl you did not create. In this project nothing is pickled:

  • Data: JSON (articles.json, golden set as JSONL), readable and diff-able.
  • Embedding and reranker weights: downloaded from Hugging Face as safetensors (pure tensors, no code).
  • The vector index: Qdrant's own storage and snapshots.
  • The "model" we register: a JSON rag_config (prompt version, embedding model, top-k, thresholds).

ONNX (a portable model graph) matters when you run a local model in a different runtime (C++, edge, OpenVINO). Our generator is served by vLLM, so ONNX is optional here; it appears in Phase 7 only if exporting the reranker measurably speeds up the CPU path.

الـ pickle بيشغّل كود وإنت بتفتحه. عمرك ما تفتح .pkl مش إنت اللي عامله. في المشروع ده مفيش حاجة pickle:

  • الداتا: JSON (articles.json، والأسئلة الذهبية JSONL)، تتقري وتتقارن.
  • أوزان الـ embedding والـ reranker: من Hugging Face بصيغة safetensors (tensors بس، من غير كود).
  • الـ vector index: الـ storage والـ snapshots بتوع Qdrant نفسه.
  • "الموديل" اللي بنسجله: ملف JSON اسمه rag_config (نسخة الـ prompt، موديل الـ embedding، الـ top-k، والحدود).

ONNX (graph للموديل يشتغل في أي مكان) بيفرق لما تشغّل موديل محلي في runtime تاني (C++، edge، OpenVINO). الـ generator عندنا بيتخدم بـ vLLM، فالـ ONNX اختياري هنا؛ هيظهر في المرحلة 7 بس لو تصدير الـ reranker سرّع الـ CPU فعلاً بأرقام.

8. Structured logging and correlation IDs8. الـ Logging المنظم والـ correlation ID

"print() is not logging." Every log line is one JSON object with a timestamp, level, logger name, event and fields. Machines can filter it ("show all stage=rerank lines slower than 500 ms").

A correlation ID (request_id) is created when a request arrives, stored in a context variable, added to every log line of that request, returned in the X-Request-ID header, and attached to the Langfuse trace. One ID joins the log line, the trace and the user's complaint.

Levels: DEBUG details for developers, INFO normal events (answer served in 1.2 s), WARNING odd but handled (Jev timed out, fell back to local), ERROR failed (LLM unreachable). We never log raw personal data; questions are logged as length + hash where needed.

"الـ print() مش logging." كل سطر log عبارة عن JSON فيه الوقت، والمستوى، واسم الـ logger، والحدث، وحقول زيادة. الماكينات تقدر تفلتره ("وريني كل سطور stage=rerank اللي خدت أكتر من 500 ملي ثانية").

الـ correlation ID (request_id) بيتعمل أول ما الطلب يوصل، ويتحفظ في context variable، ويتضاف لكل سطر log في الطلب ده، ويرجع في header اسمه X-Request-ID، ويتربط بالـ trace في Langfuse. ID واحد بيربط سطر الـ log والـ trace وشكوى المستخدم.

المستويات: DEBUG تفاصيل للمطورين، INFO أحداث عادية (الإجابة خلصت في 1.2 ثانية)، WARNING حاجة غريبة بس اتعاملنا معاها (Jev اتأخر فرجعنا للـ local)، ERROR حاجة فشلت (الـ LLM مش بيرد). ومش بنسجل بيانات شخصية خام؛ السؤال بيتسجل طوله وhash ليه لو احتجنا.

9. Testing9. الـ Testing

  • Unit tests check one function: does the parser find Article 147? does normalization turn أ into ا?
  • Integration tests check parts together: does POST /ask return 422 for an empty question and a valid schema for a good one?
  • Evaluation tests check quality on the golden set (RAGAS). These are slow and cost money, so CI runs a small smoke set.

Tools from Session 1: fixtures (shared setup such as sample articles or a test client), mocks (fake Qdrant/LLM/Jev so unit tests never call real services: "you are testing the API, not the model"), parametrize (one test, many inputs), and a coverage gate: CI fails under 80%.

We work test-first (TDD): write the test, watch it fail for the right reason, write the smallest code that passes, then clean up. A test that never failed proves nothing.

  • Unit tests بتختبر function واحدة: الـ parser لقى المادة 147؟ الـ normalization حوّل أ لـ ا؟
  • Integration tests بتختبر أجزاء مع بعض: POST /ask بيرجع 422 لو السؤال فاضي، وشكل رد صح لو السؤال كويس؟
  • Evaluation tests بتقيس الجودة على الأسئلة الذهبية (RAGAS). دي بطيئة وبفلوس، فالـ CI بيشغّل مجموعة صغيرة بس.

أدوات السيشن الأولى: الـ fixtures (تجهيز مشترك زي مواد للتجربة أو test client)، والـ mocks (Qdrant وLLM وJev مزيفين عشان الـ unit tests متناديش خدمات حقيقية: "إنت بتختبر الـ API مش الموديل")، والـ parametrize (test واحد بمدخلات كتير)، وبوابة الـ coverage: الـ CI يفشل لو أقل من 80%.

بنشتغل test-first (TDD): نكتب الـ test، نشوفه بيفشل للسبب الصح، نكتب أصغر كود يخليه ينجح، وبعدين ننضف. الـ test اللي عمره ما فشل مبيثبتش حاجة.

10. Code quality gates10. بوابات جودة الكود

Ruff is one fast tool that lints (finds bugs and bad patterns) and formats (one style for everyone). It replaces flake8, isort and black. We also enable a rule that forbids print() in src/.

pre-commit runs ruff, whitespace fixers, a YAML checker and a secret scanner on every git commit. "The hook is a convenience; the CI workflow is the guarantee": anyone can skip a local hook with --no-verify, so CI runs the same checks again on every pull request.

Ruff تول واحدة سريعة بتعمل lint (بتلاقي bugs وأنماط وحشة) وformat (ستايل واحد للكل). جت بدل flake8 وisort وblack. وفعّلنا قاعدة بتمنع print() جوه src/.

pre-commit بيشغّل ruff ومظبّطات المسافات وفاحص YAML وفاحص أسرار مع كل git commit. "الـ hook راحة، والـ CI هو الضمان": أي حد يقدر يتخطى الـ hook المحلي بـ --no-verify، فالـ CI بيعيد نفس الفحوصات على كل pull request.

11. Docker and Compose11. Docker وCompose

Docker solves "it works on my machine". An image is a frozen template (like a class); a container is a running instance of it (like an object). Changes inside a container disappear unless you build a new image or use a volume.

  • Layers and cache: copy pyproject.toml + uv.lock and install dependencies before copying src/. Code changes often, dependencies rarely, so rebuilds take seconds.
  • Multi-stage build: a builder stage installs everything; the runtime stage copies only the result. Smaller image, fewer vulnerabilities.
  • Non-root user, a HEALTHCHECK, a .dockerignore (no .git, .venv, data), and pinned tags: latest is not "newest", it is just a label.
  • Compose runs several containers together. Service names are hostnames on a shared network: the API reaches http://qdrant:6333.

Docker بيحل مشكلة "شغال عندي على جهازي". الـ image قالب ثابت (زي الـ class)؛ والـ container نسخة شغالة منه (زي الـ object). أي تغيير جوه الـ container بيروح إلا لو عملت image جديدة أو استخدمت volume.

  • الـ layers والـ cache: انسخ pyproject.toml وuv.lock وسطّب المكتبات قبل ما تنسخ src/. الكود بيتغير كتير والمكتبات نادرًا، فالـ rebuild ياخد ثواني.
  • Multi-stage build: مرحلة builder بتسطّب كل حاجة، ومرحلة runtime بتاخد الناتج بس. image أصغر وثغرات أقل.
  • user مش root، وHEALTHCHECK، و.dockerignore (من غير .git ولا .venv ولا الداتا)، وtags متثبتة: latest مش معناها "الأحدث"، دي مجرد اسم.
  • Compose بيشغّل كذا container مع بعض. اسم الـ service بيبقى hostname على الشبكة: الـ API بيوصل لـ http://qdrant:6333.

Profiles keep the laptop alive. The full stack (Qdrant, Redis, Postgres, MinIO, MLflow, vLLM, Prometheus, Grafana, Langfuse, Airflow…) does not fit in 16 GB at once, so each service belongs to a profile and you start only what the current task needs.

الـ Profiles بتحافظ على اللابتوب. الـ stack كله (Qdrant وRedis وPostgres وMinIO وMLflow وvLLM وPrometheus وGrafana وLangfuse وAirflow…) مش هيدخل في 16 جيجا مرة واحدة، فكل service تابعة لـ profile وبتشغّل اللي المهمة الحالية محتاجاه بس.

12. Git, pull requests and tags12. Git والـ Pull Requests والـ tags

Never commit straight to main. Each phase gets a branch (module-2-rag-api), small commits that explain why, a pull request with the numbers measured and screenshots, a green CI run, and after merge a tag (v0.1.0…v1.0.0). Branch protection makes "no green CI, no merge" a rule, not a wish.

Commit messages follow a simple convention: feat: new behaviour, fix: bug, test:, docs:, chore:. "fix bug" is not a commit message.

Why tags matter: the reviewer checks out v0.2.0 and gets exactly what the report describes. Together with DVC and MLflow, a tag is the start of the lineage chain.

عمرك ما تعمل commit على main مباشرة. كل مرحلة ليها branch (module-2-rag-api)، وcommits صغيرة بتشرح ليه، وpull request فيه الأرقام اللي قسناها وصور، وCI أخضر، وبعد الـ merge نعمل tag (v0.1.0 لحد v1.0.0). الـ branch protection بيخلي "مفيش CI أخضر، مفيش merge" قاعدة مش أمنية.

رسايل الـ commit ليها نظام بسيط: feat: حاجة جديدة، fix: إصلاح، test:، docs:، chore:. "fix bug" مش رسالة commit.

ليه الـ tags مهمة: اللي بيراجع يعمل checkout لـ v0.2.0 فيلاقي بالظبط اللي التقرير بيوصفه. ومع DVC وMLflow، الـ tag هو أول حلقة في سلسلة الـ lineage.
